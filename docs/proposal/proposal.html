Project at a glance

Sentinel DNS is a DNS server for a lab network, built on BIND 9 inside an Ubuntu 24.04 virtual machine. It answers names for the lab's own zone (lab.local), resolves Internet names for lab clients, signs its zone with DNSSEC, and blocks malware, phishing and tracking domains with a DNS firewall (Response Policy Zone) fed by real public threat lists.

Administrators manage everything through an HTTPS web dashboard or a command-line tool (dnsctl); every change is validated, checked by BIND's own tools and applied without restarting the server. Installation and testing are automated with shell scripts.

1Problem Statement & Objective

Background

The Domain Name System (DNS) turns names such as www.example.com into IP addresses. Almost every network connection — web, e-mail, software updates — starts with a DNS lookup, so the DNS server a computer uses decides where that computer connects.

The problem

  • No control: small labs and campuses usually rely on the ISP's or the router's default resolver. The network admin cannot see, filter or fix anything.
  • Spoofing and cache poisoning: plain DNS answers are not authenticated. A forged answer can silently send a user to a fake bank or login page.
  • Malware and phishing: malicious and tracking domains resolve freely. DNS is the cheapest place to stop them — before any connection is made — but nobody filters it.
  • No local names: lab servers, printers and VMs have no names; users memorise and mistype IP addresses.
  • Error-prone administration: managing BIND means editing zone files by hand. One typo or a forgotten serial number takes the zone down, and there is no record of who changed what.
  • Open resolvers: a badly configured server answers anyone on the Internet and can be abused for DDoS amplification attacks.

Why it matters

  • DNS is a single point of failure and a single point of protection for the whole network.
  • Social impact: protects students and staff from phishing and malware; gives accountability (audit trail of admin actions) while respecting privacy (limited log retention, client-IP anonymisation, logs visible only to admins).
  • It is a realistic Linux system-administration task that exercises core OS topics: files and permissions, processes and services, scheduling, networking and security.

2Project Scope

In scope — we WILL build

  • Ubuntu 24.04 server VM in VirtualBox with a static IP on a host-only lab network
  • BIND 9: forward zone lab.local, reverse zone 56.168.192.in-addr.arpa, caching, forwarders
  • Record types A, AAAA, CNAME, MX, TXT, NS, PTR
  • DNSSEC: KSK/ZSK keys, automatic signing, DS record, validation of external answers
  • Recursion restricted to the lab ACL; response rate limiting
  • DNS firewall (RPZ): threat feeds for malware, phishing, ads/trackers, crypto-mining, adult, gambling, social; category on/off; custom allow/block rules; 6-hourly automatic refresh
  • HTTPS web dashboard: records, policies, threat log, analytics, users & roles, settings
  • dnsctl command-line tool
  • install.sh and measure.sh shell scripts, systemd services/timers, automated tests

Out of scope — we will NOT build

  • A public, Internet-facing DNS service (open-resolver / DDoS risk)
  • A secondary (slave) DNS server or zone transfers
  • DNS-over-TLS / DNS-over-HTTPS
  • A trained machine-learning model (only a rule-based risk score)
  • DHCP, mail server, web proxy or content filtering of pages
  • High availability, load balancing or multi-site deployment
  • Registering a real public domain

Assumptions & constraints

  • Each member has a laptop with VirtualBox; the VM gets 2 vCPU, 2–4 GB RAM
  • Internet access (NAT) available for packages and threat feeds
  • Lab clients are PCs/VMs on 192.168.56.0/24

4Proposed System Design

Figure 1 — Architecture of Sentinel DNS

Components

ComponentRole
BIND 9 (named)Answers every DNS query: authoritative for lab.local and the reverse zone, recursive with cache for Internet names, applies the RPZ firewall, signs and validates with DNSSEC.
Response Policy ZonesTwo policy zones: rpz.local (admin rules, checked first) and rpz-feeds.local (downloaded threat lists). A match returns NXDOMAIN instead of the real address.
Sentinel core (Python)Keeps zones, rules and history in SQLite; generates BIND's configuration, zone and policy files; checks them; swaps them in atomically; reloads BIND with rndc.
Web dashboard (Flask + nginx)HTTPS front end: Dashboard, Domains, Policies, Threats, Analytics, Query Tester, Users, Settings.
dnsctlTerminal front end using the same core: status, record add, block add, logs, sync, check.
Feed updatersystemd timer + service that downloads and parses public threat lists every 6 hours.
Log ingesterReads BIND's query log and statistics into the database for the threat log and charts.

Workflow 1 — answering a query

  1. A lab client asks 192.168.56.10 for a name (UDP/TCP 53).
  2. BIND checks the client against the ACL; outsiders get REFUSED.
  3. The name is checked against the policy zones; a match returns NXDOMAIN and is logged as a threat.
  4. If the name is in lab.local, BIND answers from its signed zone.
  5. Otherwise it answers from cache, or resolves recursively, validates DNSSEC and caches the answer.

Workflow 2 — an admin change (safe change pipeline)

  1. Admin adds/edits a record or rule in the dashboard or with dnsctl.
  2. Input is validated (name syntax, IP format, CNAME conflicts, control characters).
  3. The new zone file is generated with a higher SOA serial and checked by named-checkzone / named-checkconf.
  4. Only if the check passes is the file swapped in atomically and BIND reloaded with rndc; otherwise the old zone keeps serving and the admin sees the error.
  5. The action is written to the audit log.

Workflow 3 — threat-feed update

  1. The systemd timer starts the feed service every 6 hours (and on demand via “Sync Feeds”).
  2. Feeds are downloaded, parsed and de-duplicated; enabled categories are written to rpz-feeds.local.
  3. The zone is checked and reloaded; a failed download keeps the previous list.

9Expected Challenges & Trade-offs

Conflicting constraints

Trade-offOur decision and why
Security vs. usabilityRecursion only for the lab ACL and an HTTPS-only dashboard with login limits — but a GUI and CLI so admins never edit raw files, and a viewer role for read-only access.
Blocking vs. false positivesStrong feeds catch more threats but can block real sites. We add category on/off switches, an allow list that overrides every feed and one-click unblock from the threat log.
Performance vs. resourcesA 340,000-name blocklist and DNSSEC cost memory and CPU on a small VM. We rely on caching, keep the stack light (SQLite, no containers) and measure latency with and without the firewall.
Privacy vs. accountabilityQuery logs help find infected machines but reveal browsing. Logs are admin-only, kept for a limited time and client IPs can be anonymised; admin actions are always audited.
Availability vs. safety of changesEvery change is checked before it is applied, which adds a second of delay — but a bad change can never take the zone down.

Risks and mitigation

RiskLikelihoodImpactMitigation
A wrong zone file stops DNSMediumHighnamed-checkzone before apply, atomic swap, old zone kept
DNSSEC misconfiguration (expired signatures)MediumHighBIND's automatic dnssec-policy; validation test in measure.sh
Feed download fails or is hugeMediumMediumKeep the previous list; timeouts; size check
Browsers use DNS-over-HTTPS and bypass the firewallHighMediumDocumented limitation; disable “secure DNS” on lab clients
Slow laptops / VirtualBox performanceMediumMediumSmall VM, close heavy apps, snapshots; demo fallback mode on Windows
Member unavailable during examsMediumMediumEach part documented and reviewed by a second member; feature freeze at end of W5
